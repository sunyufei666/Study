## 索引

### 常见模型

哈希表：等值查询，不适合范围查询

有序数组：适合静态存储场景，不适合表更新

二叉搜索树：会形成一个极端的链表；如果数据量过大，还会造成树的高度过高，因为索引是会存到磁盘里的，磁盘IO的效率比较低，过高的层数会导致检索效率下降

### InnoDB索引模型

 每个索引都是一个B+树

#### 主键索引和非主键索引

根据叶子节点的内容分为主键索引和非主键索引，因为主键索引存储的是完整的行数据，所以主键索引又叫聚簇索引；非主键索引里面存的是主键的值，所以非主键索引又叫二级索引，常说的回表就是查到主键的值，再从主键索引里查

![image-20260818173605526](./image-20260818173605526.png)

页分裂与页合并：元素的插入和删除导致

如果直接查询主键，会减少回表次数，因为会覆盖查询请求，所以叫覆盖索引

如果有需要，可以创建联合索引，将唯一值和结果列创建联合索引（例如身份证号和名字 ），形成覆盖索引，减少回表次数

#### 最左前缀原则

可以匹配联合索引第一个字段的前n个字符，直到不满足条件为止

**在建立联合索引的时候，如何安排索引内的字段顺序？**

如果通过调整顺序，可以少维护一个索引，那这个顺序往往就是需要优先考虑采用的

空间

可以在索引遍历的过程中对索引里包含的字段先判断，直接过滤掉不满足条件的记录，减少回表次数

#### 唯一索引、普通索引

查询过程性能的差距微乎其微，因为把数据页读到内存里（16kb）做操作造成的性能影响不大

把更新操作记录到change buffer，能减少读磁盘操作，避免占用内存，显著提高内存利用率

唯一索引的更新不会用到change buffer，因为更新时会先将数据页读取到内存里，判断插入的值是否已经存在，如果存在，这时候直接操作内存会更快一点；只有普通索引的更新会用到，并且在写多读少的业务场景里效率是最高的，但是如果是写少读多的时候，会频繁进行merge操作，反而会降低执行效率

#### 索引选择

**优化器**通过采样统计估算索引基数，根据基数来判断使用的索引

在选择索引时，优化器会把回表的代价也算进去

**如果选错？**

1. 可以通过analyze table t;重新统计下索引基数
2. force index(a)

3. 修改sql语句，引导mysql，例如order by b，优化器会认为查出来的b就是有序的，直接就会用索引b

#### 前缀索引

用前缀索引容易导致查询语句读数据的次数变多

```
alter table user add index index2(email(6));
```

用了前缀索引就用不了覆盖索引对查询的性能优化了

提高数据区分度的手段：倒叙存储(reverse)、hash字段(crc32)

**要查询的那条数据，内存里没有，而磁盘上的页还是旧数据，后台还没来得及刷怎么办？**

### 事务

myisam是不支持事务的

事务的特性ACID，原子性，一致性，隔离性，持久性

**事务的隔离级别**

读未提交：一个事务还没提交时，它做的变更就能被别的事务看到

读已提交：一个事务提交之后，它做的变更才会被其他事务看到

可重复度：一个事务执行过程中看到的数据，总是跟这个事务在启动时看到的数据是一致的

串行化：对于同一行记录，“写”会加“写锁”，“读”会加“读锁“

读已提交和可重复读都会创建一个readview，但是创建的时机不一样

#### MVCC（多版本并发控制）

**为什么尽量不要使用长事务？**

如果表有大量更新，Undo Log会疯狂累积，导致`ibdata`或独立Undo表空间文件持续增大，直到打满磁盘。即使后来把这个长事务回滚了，物理文件空间也可能无法立即释放（取决于配置），造成“磁盘写满，数据库只读”的严重事故

MDL元数据锁、行锁长期被持有，无法释放，还可能会出现死锁问题

主从复制延迟，写入binlog内容过多，导致从库无法短时间内消化

Redolog无法推进检查点，空间无法被循环覆盖利用

**事务的启动方式**

set autocommit=1  // 启动事务自动提交，设置后，只有用begin显式开启事务，才需要手动commit提交

如果事务开启比较频繁的话，可以使用commit WORK and CHAIN提交当前事务并开启新事务。

```sql
information_schema.innodb_trx   TIME_TO_SEC(timediff(now(),trx_started))>60; // 判断长事务
```


事务c在事务b执行“当前读”之后提交，但是因为事务c持有锁，事务b当前读会被锁住，只有等c提交事务之后，b才会继续执行

### 数据页

![image-20260822122039020](./image-20260822122039020.png)

每一组的最后一个记录头信息里面会存当前组一共有多少条记录

- **有序单链表**：页内的所有用户记录（User Records），会**按照主键值从小到大**的顺序，通过记录头信息中的 `next_record` 属性串联成一个**单向链表**。这个链表的头尾就是 Infimum 和 Supremum 这两条虚拟记录。
- **页目录（Page Directory）实现二分查找**：
  1. **分组**：InnoDB会将这个链表中的记录分成若干个小组。
  2. **建“槽”**：每个组的**最后一条记录**的地址偏移量，会被抽取出来，按顺序存放在 Page Directory 中，形成一个**槽（Slot）数组**。
  3. **查找**：当需要根据主键查找一条记录时，会先在 Page Directory 的“槽”数组中进行**二分查找**，快速定位到记录所在的小组。然后，再在小组内部通过 `next_record` 指针进行**顺序遍历**，找到最终的目标记录。

### 自适应Hash索引

自适应哈希索引是Innodb在buffer pool中自动创建和维护的一个内存中的哈希索引结构，不是由用户主动创建的。

### BufferPool管理

![image-20260823165813024](./image-20260823165813024.png)



**LRU**（最近最少使用）

提高缓存命中率

当访问的页在buffer pool里，就直接把页对应的LRU链表节点移动到链表的头部。

当访问的页不在buffer pool里，把页放入到LRU链表的头部，并且淘汰LRU链表末尾的节点。

![image-20260823170409222](./image-20260823170409222.png)

buffer pool的三种空间：clean page（被使用过的空间，但是数据和磁盘是一致的）、dirty page（被使用的空间，但是数据和磁盘不一致）、free page（没有被使用的空间）

预读机制：加载页时，会将“很可能”会被访问的数据页加载到内存缓冲池中，这个机制的核心目的是将多次零散的小规模磁盘读取，合并为少数几次大规模的连续读取，从而显著减少磁盘I/O次数，提升查询性能

**预读失效**：InnoDB将物理上相邻的数据页提前加载到Buffer Pool（缓冲池）后，这些数据页最终却完全没有被后续的查询访问到，白白浪费了宝贵的内存空间，并挤占了热点数据页的现象

将LRU链表分为两个区域，young区域和old区域

![image-20260823172445772](./image-20260823172445772.png)

**buffer pool污染**：如果预读进来的**大量数据页**最终没有被任何查询使用，它们会占用宝贵的缓冲池内存，并“挤掉”那些真正热点的、频繁访问的数据页，导致缓冲池的命中率下降，反而损害整体性能

**脏页刷盘时机**

redolog（write ahead log）日志满、buffer pool空间不足、mysql空闲、mysql正常关闭
